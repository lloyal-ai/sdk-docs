<h1 id="distance-is-not-a-criterion">Distance is not a criterion</h1>
<p><strong>Most systems choose what enters context by distance.</strong> They embed the candidate, embed the query, keep whatever lands closest. Distance is cheap, and it is not a judgement.</p>
<p>Consider two sentences:</p>
<div class="code-frame"><div class="code-label">CANDIDATE</div><pre><code>Query:    The inspection occurred on 18 March.

Passage:  The inspection was scheduled for 18 March
          but was cancelled on 17 March.</code></pre></div>
<p>Same entities, same date, heavy lexical overlap &mdash; neighbours in embedding space. Top-k returns the passage, your model states the assertion as fact, and you have spent scarce context on the one document that refutes it.</p>
<p>Negation and modality are invisible to similarity, because similarity was never asked anything. It measured.</p>

<h1 id="the-question-is-a-sentence">The question is a sentence</h1>
<p><strong>Every chunk that reaches a model&rsquo;s attention in Lloyal got there because a second model was asked a question in English and answered yes or no.</strong> The judge is a prompt, and the criterion lives in one line of it:</p>
<div class="code-frame"><div class="code-label">THE JUDGE</div><pre><code>SYSTEM: Judge whether the Document meets the requirements based on
        the Query and the Instruct provided. Note that the answer
        can only be "yes" or "no".

USER:   &lt;Instruct&gt;: Given a web search query, retrieve relevant
                    passages that answer the query
        &lt;Query&gt;:    ...
        &lt;Document&gt;: ...</code></pre></div>
<p>The score is <code>logit("yes") &minus; logit("no")</code> &mdash; two slots out of a hundred and fifty thousand, read as log-odds. A floor of zero means <em>keep what the judge would call relevant</em>, which is a threshold you can say out loud.</p>
<p>Because the criterion sits in the <code>&lt;Instruct&gt;</code> line, the same weights answer a different question when the sentence changes. That line is the plane you bring into focus. Similarity has one plane, fixed at <em>looks alike</em>, and no way to move it at any price.</p>

<h1 id="a-page-arrives-in-its-own-words">A page arrives in its own words</h1>
<p><strong>An agent fetches a forty-thousand-token page. Two thousand tokens of it reach the model.</strong> The article is chunked on heading boundaries, every chunk is scored, and the survivors are admitted <em>verbatim</em> &mdash; five of them by default, inside a 2048-token budget.</p>
<p>Nothing is summarised. The industry&rsquo;s answer to an oversized page is a second generative call that compresses it, which is lossy, slow, and precisely where fabrication enters. Selection replaces compression: what arrives is the source&rsquo;s own sentences, quotable and attributable, chosen by a question you wrote.</p>
<div class="code-frame"><div class="code-label">ADMITTING FROM A PAGE</div><pre><code><span class="c">// 1. structure the page — headings become chunk boundaries</span>
const chunks = yield* call(() =&gt;
  chunkHtml(fetched.articleHtml, url, fetched.title),
);

<span class="c">// 2. ask the judge once per chunk, in one batched pass</span>
let scored: ScoredChunk[] = [];
for await (const batch of reranker.score(args.query, chunks)) {
  scored = batch.results;
}

<span class="c">// 3. admit verbatim: top-K, inside a token budget</span>
const topChunks = selectTopChunks(scored, chunks, topK, tokenBudget);</code></pre></div>
<p>If you have written retrieval before, step three is where your <code>top_k</code> slice went. The difference is what step two returns &mdash; not a distance to sort by, but an answer to a question &mdash; and that there is no step four. Nothing compresses what survived.</p>

<p>A corpus admits on the same shape, with one addition. The judge is linear in candidates, so a cheap lexical stage narrows the field before it is asked anything:</p>
<div class="code-frame"><div class="code-label">ADMITTING FROM A CORPUS</div><pre><code><span class="c">// a cheap first stage decides who gets judged at all</span>
const candidates = bm25.topK(query, 100);

<span class="c">// the judge scores those, in one batched pass</span>
const scored = await reranker.score(query, candidates);

<span class="c">// a floor you can say out loud: keep what the judge calls relevant</span>
const hits = scored.filter((s) =&gt; s.score &gt;= threshold);</code></pre></div>
<p>The floor does double duty. Above it the agent has confident matches. Below it the agent has learned something too &mdash; that this corpus does not answer the question as asked, and the next move is a different question rather than a longer list.</p>
<p><strong>And the same lens admits work, not only text.</strong> Hand it proposed sub-tasks instead of passages and it asks two questions before anything is spawned:</p>
<div class="code-frame"><div class="code-label">ADMITTING WORK</div><pre><code><span class="c">// does this sub-task still follow from the original query?</span>
const onTopic = await scorer.scoreEntailmentBatch(subTasks);
const surviving = subTasks.filter((_, i) =&gt; scorer.shouldProceed(onTopic[i]));

<span class="c">// is someone further up the tree already asking it?</span>
const ancestors = callingAgent.walkAncestors((a) =&gt; (a.task ? [a.task] : []));
const echo = await scorer.scoreSimilarityBatch(ancestors.join(" "), surviving);
if (Math.min(...echo) &gt; echoThreshold) return { error: "already asked upstream" };</code></pre></div>
<p>Same primitive, same batched pass, a different reference string. Admission is not a retrieval feature &mdash; it is what the runtime does whenever something wants space it has not earned.</p>

<h1 id="the-aperture-is-under-program-control">The aperture is under program control</h1>
<p><strong>Policy decides what the model gets to focus on, per agent, per tick.</strong> Reading a page in explore mode, chunks are scored against what that agent just asked. In exploit mode they must satisfy the agent&rsquo;s query <em>and</em> the original task at once &mdash; <code>min(toolQueryScore, originalQueryScore)</code>, which is a much narrower depth of field.</p>
<p>The default is wide. <code>AgentPolicy.shouldExplore()</code> narrows it as headroom disappears, at 40% of context and 50% of the time budget in the shipped policy. An investigating agent keeps its bridging content while there is room for it, and stops down when there is not.</p>
<div class="code-frame"><div class="code-label">THE POSTURE SWITCH</div><pre><code><span class="c">// Explore (default): score against what this agent asked for.</span>
<span class="c">// Exploit: demand both planes at once.</span>
if (!context?.explore &amp;&amp; context?.scorer) {
  const combined = yield* call(() =&gt;
    context.scorer.scoreRelevanceBatch(chunkTexts, args.query),
  );  <span class="c">// min(toolQueryScore, originalQueryScore)</span>
  scored = scored
    .map((sc, i) =&gt; ({ ...sc, score: combined[i] }))
    .sort((a, b) =&gt; b.score - a.score);
}</code></pre></div>
<p>The reason explore is the default when reading a page is worth stating: the agent chose that page. Scoring its contents against the original task would demote exactly the bridging material that produces the next good hypothesis.</p>

<h1 id="a-hundred-candidates-one-pass">A hundred candidates, one pass</h1>
<p><strong>Widen the candidate set and the GPU bill stays flat.</strong> Scoring forks a branch per candidate and dispatches them together: every token carries its own position and sequence, logits requested only on each candidate&rsquo;s final token, and one <code>llama_decode</code> settles the group. Forking shares the parent&rsquo;s cache cells rather than copying them, so a candidate costs its own tokens and nothing more.</p>
<p>You pay in cache space, not in dispatches. The group is bounded by available sequence leases, never by how many candidates you had.</p>
<p><strong>And it runs beside generation, never in front of it.</strong> The reranker owns a separate context and serialises its own calls, so admission queues among itself while the tokens already generating keep generating. Search declares <code>fanout = true</code> precisely because it touches no main-context state.</p>

<h1 id="a-threshold-is-worth-its-canaries">A threshold is worth its canaries</h1>
<p><strong>The classifier is measured before it is handed to you, and the gate refuses to return one that fails.</strong> Three checks run at startup: <code>"yes"</code> and <code>"no"</code> must each tokenise to exactly one token, or the subtraction is not a log-odds ratio at all; sentinel probes confirm the tokenizer did not merge across the prompt&rsquo;s segment boundaries; and a known-relevant and a known-irrelevant document must separate by more than one logit &mdash; the gate asserts the <em>gap</em>, not the sign.</p>
<p>This is the load-bearing consequence for anyone writing a new <code>&lt;Instruct&gt;</code>: <strong>a gate is only as good as its fixtures.</strong> The shipped canaries measure retrieval. A different question &mdash; support, entailment, policy conformance &mdash; needs canaries built for that question, or startup will happily certify a judge nobody has measured.</p>

<h1 id="lenses-that-ship">Lenses that ship</h1>
<p>Four admissions come configured, and one Ability deliberately has none.</p>

<tr><td><code>corpus / search</code></td><td>Retrieval relevance</td><td>BM25 narrows to a hundred lexical candidates, the cross-encoder scores those, and a threshold floor decides. The floor gives the agent two signals rather than one: confident matches, or a landscape worth grepping.</td></tr>
<tr><td><code>web / fetch_page</code></td><td>The agent&rsquo;s own query</td><td>Five verbatim chunks inside 2048 tokens, chosen from a page structured on its headings.</td></tr>
<tr><td><code>web / web_search</code></td><td>Provider score, then entailment</td><td>In exploit mode, <code>min(provider score, entailment score)</code> &mdash; the search engine&rsquo;s own relevance and the original task must agree. <h1 id="lenses-you-can-compose">Lenses you can compose</h1>
<p>A lens is a plane, an aperture and a budget. Change any of them and you have a different one. These are described elsewhere in the docs as procedures; each is an admission decision underneath:</p>
<ul>
<li><strong>Support judgement.</strong> Ask whether a passage supports an assertion rather than whether it resembles one. Same primitive, different sentence &mdash; and a third outcome worth keeping, because partial support, imprecise dates and scheduled-versus-occurred deserve <em>uncertain</em> rather than a coin toss.</li>
<li><strong><a href="/continuous-context#evidence-admission-by-applicability">Evidence admission by applicability</a>.</strong> Relevant is not the same as applicable. A filing can be on point and superseded; a rule can be authoritative and not yet in force.</li>
<li><strong><a href="/thinking-in-lloyal#burden-of-proof-scaling">Burden-of-proof scaling</a>.</strong> Raise the floor as the stakes rise. The threshold is a number in your policy, not a constant in ours.</li>
<li><strong><a href="/thinking-in-lloyal#temporal-applicability">Temporal applicability</a>.</strong> Admit against a date, not just a topic.</li>
<li><strong><a href="/thinking-in-lloyal#dynamic-retrieval-phase-switching">Dynamic retrieval phase switching</a>.</strong> Move the plane as the investigation moves.</li>
</ul>
<p>The first of those is the one to read twice before shipping. A new question needs new canaries, and a judge nobody measured will certify anything.</p>

<h1 id="the-shipped-lens-is-one-configuration">The shipped lens is one configuration</h1>
<p>Every element unscrews.</p>
<div class="table-wrap"><table><thead><tr><th>element</th><th>ships as</th><th>or</th></tr></thead><tbody>
<tr><td>The judge</td><td>Four batched scorers &mdash; entailment, relevance, similarity, and a shared threshold gate</td><td>Any object with a <code>scoreBatch</code> method satisfies the contract</td></tr>
<tr><td>The plane</td><td>One <code>&lt;Instruct&gt;</code> sentence, tuned for retrieval</td><td>Write another, and calibrate it</td></tr>
<tr><td>The aperture</td><td><code>DefaultAgentPolicy</code> implements all eleven hooks the pool calls</td><td>Subclass it and override the one decision you care about</td></tr>
</tbody></table></div>
<p>The scorer arrives with an <a href="/abilities">Ability</a>; the posture comes from <a href="/agent-policy-and-context-pressure">AgentPolicy</a>. Explore and exploit are one shape of one hook, not the axis itself. A policy that needs a different posture &mdash; a verification phase, a burden-of-proof that rises with the stakes &mdash; writes it.</p>
<p>An embedding has none of this. Not a plane you can choose, not a posture to switch, not a hook to override. You get similarity, forever, and you find out at review time.</p>
