A focal lens for context admission

You choose the plane that comes up sharp, and everything else falls away

The squeeze

On a laptop you have 32k, and a dozen agents that all want it.

Every search hit, every fetched page, every tool return is a candidate for space that is already spoken for. Nothing is admitted for free, so something has to choose — and at the edge that choice is the difference between an application that works and one that thrashes.

The swing

On two B200s the same application hands one agent a 57,000-word budget.

One process, both GPUs, the same packages you ran on the laptop. Nothing in the code changes between them. The policy reads the headroom it actually has, and the lens admits accordingly.

Distance is not a criterion

Most systems choose what enters context by distance. They embed the candidate, embed the query, keep whatever lands closest. Distance is cheap, and it is not a judgement.

Consider two sentences:

CANDIDATE
Query:    The inspection occurred on 18 March.

Passage:  The inspection was scheduled for 18 March
          but was cancelled on 17 March.

Same entities, same date, heavy lexical overlap — neighbours in embedding space. Top-k returns the passage, your model states the assertion as fact, and you have spent scarce context on the one document that refutes it.

Negation and modality are invisible to similarity, because similarity was never asked anything. It measured.

The question is a sentence

Every chunk that reaches a model’s attention in Lloyal got there because a second model was asked a question in English and answered yes or no. The judge is a prompt, and the criterion lives in one line of it:

THE JUDGE
SYSTEM: Judge whether the Document meets the requirements based on
        the Query and the Instruct provided. Note that the answer
        can only be "yes" or "no".

USER:   <Instruct>: Given a web search query, retrieve relevant
                    passages that answer the query
        <Query>:    ...
        <Document>: ...

The score is logit("yes") − logit("no") — two slots out of a hundred and fifty thousand, read as log-odds. A floor of zero means keep what the judge would call relevant, which is a threshold you can say out loud.

Because the criterion sits in the <Instruct> line, the same weights answer a different question when the sentence changes. That line is the plane you bring into focus. Similarity has one plane, fixed at looks alike, and no way to move it at any price.

A page arrives in its own words

An agent fetches a forty-thousand-token page. Two thousand tokens of it reach the model. The article is chunked on heading boundaries, every chunk is scored, and the survivors are admitted verbatim — five of them by default, inside a 2048-token budget.

Nothing is summarised. The industry’s answer to an oversized page is a second generative call that compresses it, which is lossy, slow, and precisely where fabrication enters. Selection replaces compression: what arrives is the source’s own sentences, quotable and attributable, chosen by a question you wrote.

ADMITTING FROM A PAGE
// 1. structure the page — headings become chunk boundaries
const chunks = yield* call(() =>
  chunkHtml(fetched.articleHtml, url, fetched.title),
);

// 2. ask the judge once per chunk, in one batched pass
let scored: ScoredChunk[] = [];
for await (const batch of reranker.score(args.query, chunks)) {
  scored = batch.results;
}

// 3. admit verbatim: top-K, inside a token budget
const topChunks = selectTopChunks(scored, chunks, topK, tokenBudget);

If you have written retrieval before, step three is where your top_k slice went. The difference is what step two returns — not a distance to sort by, but an answer to a question — and that there is no step four. Nothing compresses what survived.

A corpus admits on the same shape, with one addition. The judge is linear in candidates, so a cheap lexical stage narrows the field before it is asked anything:

ADMITTING FROM A CORPUS
// a cheap first stage decides who gets judged at all
const candidates = bm25.topK(query, 100);

// the judge scores those, in one batched pass
const scored = await reranker.score(query, candidates);

// a floor you can say out loud: keep what the judge calls relevant
const hits = scored.filter((s) => s.score >= threshold);

The floor does double duty. Above it the agent has confident matches. Below it the agent has learned something too — that this corpus does not answer the question as asked, and the next move is a different question rather than a longer list.

And the same lens admits work, not only text. Hand it proposed sub-tasks instead of passages and it asks two questions before anything is spawned:

ADMITTING WORK
// does this sub-task still follow from the original query?
const onTopic = await scorer.scoreEntailmentBatch(subTasks);
const surviving = subTasks.filter((_, i) => scorer.shouldProceed(onTopic[i]));

// is someone further up the tree already asking it?
const ancestors = callingAgent.walkAncestors((a) => (a.task ? [a.task] : []));
const echo = await scorer.scoreSimilarityBatch(ancestors.join(" "), surviving);
if (Math.min(...echo) > echoThreshold) return { error: "already asked upstream" };

Same primitive, same batched pass, a different reference string. Admission is not a retrieval feature — it is what the runtime does whenever something wants space it has not earned.

The aperture is under program control

Policy decides what the model gets to focus on, per agent, per tick. Reading a page in explore mode, chunks are scored against what that agent just asked. In exploit mode they must satisfy the agent’s query and the original task at once — min(toolQueryScore, originalQueryScore), which is a much narrower depth of field.

The default is wide. AgentPolicy.shouldExplore() narrows it as headroom disappears, at 40% of context and 50% of the time budget in the shipped policy. An investigating agent keeps its bridging content while there is room for it, and stops down when there is not.

THE POSTURE SWITCH
// Explore (default): score against what this agent asked for.
// Exploit: demand both planes at once.
if (!context?.explore && context?.scorer) {
  const combined = yield* call(() =>
    context.scorer.scoreRelevanceBatch(chunkTexts, args.query),
  );  // min(toolQueryScore, originalQueryScore)
  scored = scored
    .map((sc, i) => ({ ...sc, score: combined[i] }))
    .sort((a, b) => b.score - a.score);
}

The reason explore is the default when reading a page is worth stating: the agent chose that page. Scoring its contents against the original task would demote exactly the bridging material that produces the next good hypothesis.

A hundred candidates, one pass

Widen the candidate set and the GPU bill stays flat. Scoring forks a branch per candidate and dispatches them together: every token carries its own position and sequence, logits requested only on each candidate’s final token, and one llama_decode settles the group. Forking shares the parent’s cache cells rather than copying them, so a candidate costs its own tokens and nothing more.

You pay in cache space, not in dispatches. The group is bounded by available sequence leases, never by how many candidates you had.

And it runs beside generation, never in front of it. The reranker owns a separate context and serialises its own calls, so admission queues among itself while the tokens already generating keep generating. Search declares fanout = true precisely because it touches no main-context state.

A threshold is worth its canaries

The classifier is measured before it is handed to you, and the gate refuses to return one that fails. Three checks run at startup: "yes" and "no" must each tokenise to exactly one token, or the subtraction is not a log-odds ratio at all; sentinel probes confirm the tokenizer did not merge across the prompt’s segment boundaries; and a known-relevant and a known-irrelevant document must separate by more than one logit — the gate asserts the gap, not the sign.

This is the load-bearing consequence for anyone writing a new <Instruct>: a gate is only as good as its fixtures. The shipped canaries measure retrieval. A different question — support, entailment, policy conformance — needs canaries built for that question, or startup will happily certify a judge nobody has measured.

Lenses that ship

Four admissions come configured, and one Ability deliberately has none.

lensplanewhat it admits
corpus / searchRetrieval relevanceBM25 narrows to a hundred lexical candidates, the cross-encoder scores those, and a threshold floor decides. The floor gives the agent two signals rather than one: confident matches, or a landscape worth grepping.
web / fetch_pageThe agent’s own queryFive verbatim chunks inside 2048 tokens, chosen from a page structured on its headings.
web / web_searchProvider score, then entailmentIn exploit mode, min(provider score, entailment score) — the search engine’s own relevance and the original task must agree. A result a sibling already fetched is skipped outright.
rig / delegateEntailment, then similarityAdmission of work rather than text: proposed sub-tasks that drifted from the original query are dropped, and any that echo a task already running further up the tree are refused.
wikipedia—No lens at all. A capped result list, and the model reads what comes back. Not every Ability needs one, and pretending otherwise would be the expensive kind of consistency.

Lenses you can compose

A lens is a plane, an aperture and a budget. Change any of them and you have a different one. These are described elsewhere in the docs as procedures; each is an admission decision underneath:

  • Support judgement. Ask whether a passage supports an assertion rather than whether it resembles one. Same primitive, different sentence — and a third outcome worth keeping, because partial support, imprecise dates and scheduled-versus-occurred deserve uncertain rather than a coin toss.
  • Evidence admission by applicability. Relevant is not the same as applicable. A filing can be on point and superseded; a rule can be authoritative and not yet in force.
  • Burden-of-proof scaling. Raise the floor as the stakes rise. The threshold is a number in your policy, not a constant in ours.
  • Temporal applicability. Admit against a date, not just a topic.
  • Dynamic retrieval phase switching. Move the plane as the investigation moves.

The first of those is the one to read twice before shipping. A new question needs new canaries, and a judge nobody measured will certify anything.

The shipped lens is one configuration

Every element unscrews.

elementships asor
The judgeFour batched scorers — entailment, relevance, similarity, and a shared threshold gateAny object with a scoreBatch method satisfies the contract

The scorer arrives with an Ability; the posture comes from AgentPolicy. Explore and exploit are one shape of one hook, not the axis itself. A policy that needs a different posture — a verification phase, a burden-of-proof that rises with the stakes — writes it.

An embedding has none of this. Not a plane you can choose, not a posture to switch, not a hook to override. You get similarity, forever, and you find out at review time.
